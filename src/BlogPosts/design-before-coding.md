# Clean UI Thinking: Why I Started Designing Before Coding

As a developer with a background in **cinematography**, I’ve always been drawn to visuals. In film, you don’t start shooting randomly—you plan the frame, lighting, and mood first. The same idea applies to web development.

For a long time, I used to jump straight into coding. I would open my editor, create components, and “figure out the UI along the way.” It felt fast in the beginning, but in real projects—like my GRE preparation app (**GREP**)—it started creating problems.

The app worked, but the UI didn’t feel consistent. And worse, changes became painful.

That’s when I started designing before coding.

## The Problem with the "Code-First" Way

When we start coding without a clear UI plan, we usually do something like this:

1. Create a page.
2. Add components as needed.
3. Style them quickly.
4. Fix alignment issues later.
5. Repeat the same styling in other pages.

This works for small projects, but as the app grows, it creates a messy UI system.

You start seeing issues like:

- inconsistent spacing and font sizes
- buttons looking different on every page
- layouts breaking on smaller screens
- random colors and “temporary” styling that becomes permanent
- too much time wasted on small UI fixes

Instead of focusing on the actual feature, you spend hours fixing “why this looks weird.”

## Enter Design-First Thinking

Design-first doesn’t mean you need to be a professional UI designer.

It simply means:

**Before writing code, you decide how the UI should look and behave.**

Even a rough plan helps a lot.

In my case, I started using:

- quick wireframes (even on paper)
- simple layouts in Figma
- basic design rules like spacing and typography

This one habit made my coding faster—not slower.

### The Anatomy of a Simple UI System

When I design first, I usually decide a few things before coding:

- a primary button style
- a consistent font scale (heading, subheading, body)
- spacing rules (like 8px / 16px / 24px)
- card layout style
- how forms should look across the app

Once these are decided, every new page becomes easier to build.

Because I’m not reinventing the UI every time.

## Why This Feels Better

Design-first helps because:

- your UI looks consistent across pages
- your app feels more professional
- you build components that can be reused
- responsive design becomes easier
- you reduce “random fixes” later

And the biggest benefit:

**You stop fighting the UI.**

## The Big Shift: From "Making Pages" to "Building a System"

The biggest lesson I learned is this:

A real app is not a collection of pages.

It’s a **system**.

If your design system is weak, your code becomes messy.

But if your UI system is clear, your code becomes naturally cleaner too.

In GREP, once I started designing first, things improved instantly:

- the dashboard layout became cleaner
- the study plan pages felt connected
- the buttons and inputs looked consistent
- new features were easier to add without breaking the UI

## Final Thoughts

Design-first changed my workflow in a simple but powerful way.

It made my work:

- faster
- cleaner
- more consistent
- and easier to scale

For small projects, coding directly is fine.  
But for real-world apps like GREP, designing first feels like the difference between shooting a film without a storyboard… and shooting with a clear vision.

The code still matters.

But the experience matters more.
